## 4. Giải thích phần kỹ thuật đã thực hiện

### Vấn đề cần giải quyết

Dữ liệu thô từ Crossref API có chứa nhiều thẻ HTML trong tóm tắt và tiêu đề, dữ liệu mảng bị lồng ghép và ngày tháng không chuẩn, ảnh hưởng tới chất lượng chunking và embedding của mô hình RAG. Việc làm sạch dữ liệu giúp tạo ra vector ngữ nghĩa chính xác hơn. Đồng thời, cần một bộ câu hỏi (frozen evaluation set) cố định dựa trên tập dữ liệu sạch để làm ground_truth đánh giá độ lệch (drift) khi dữ liệu bị lỗi (corrupted) và khi đã được khôi phục (repaired).

### Cách triển khai

- **Data Cleaning**: Sử dụng thư viện `re` để loại bỏ HTML tags, dùng Pandas để áp dụng lambda function, nối string (`authors_joined`, `categories_joined`), dùng datetime để tính toán khoảng thời gian `age_days` tính từ ngày xuất bản đến thời điểm hiện tại `run_date`. Cuối cùng tạo field semantic `text_for_embedding` chứa thông tin tóm gọn và ghi ra định dạng csv/json.
- **Test Set Generation**: Chỉ lấy mẫu (top 5) papers đại diện từ dataset sạch và dùng python để format thành các câu hỏi factual dựa trên các rules cố định (vd: hỏi về tác giả, ngày tháng, danh mục). Format output JSON đáp ứng nghiêm ngặt schema.

## 5. Một quyết định kỹ thuật quan trọng

- **Bối cảnh:** Lựa chọn cách tạo bộ câu hỏi đánh giá (Test Set).
- **Các phương án đã cân nhắc:** (1) Dùng LLM prompt để sinh câu hỏi tự động. (2) Tạo câu hỏi bằng template cứng (Factual Q&A) như "Ai là tác giả của...".
- **Phương án đã chọn:** Phương án 2 (Template cứng).
- **Lý do:** Tăng reproducibility (tính tái lập) vì chúng ta cần Frozen Evaluation Set. Tránh tình trạng LLM bị hallucinate khi sinh test set, cũng như giảm chi phí (cost).
- **Bằng chứng quyết định phù hợp:** Đã sinh test set tuân thủ chặt chẽ schema, có thể dùng trực tiếp để test `judge_accuracy`.

## 6. Một lỗi hoặc blocker đã xử lý

- **Triệu chứng/lỗi nguyên văn:** Xử lý `published` bị rỗng hoặc lỗi format khi map với datetime của pandas dẫn đến `NaT` / lỗi toán học.
- **Lệnh hoặc bước tái hiện:** Kiểm tra raw payload từ CrossRef API khi trường published bị thiếu.
- **Nguyên nhân gốc:** Pandas không thể trừ đi giá trị `NaT` của ngày.
- **Cách xử lý:** Thêm logic `fillna(-1)` và ép kiểu sau khi `pd.to_datetime(..., errors="coerce")`.
- **Cách xác minh sau khi sửa:** Code review và thử nghiệm với các trường hợp dữ liệu khuyết trên nháp.
- **Điều học được:** Luôn phải phòng thủ với `NaT/NaN` khi tính toán metrics trong DataFrames.

## 7. Hiểu biết về luồng end-to-end

1. Dữ liệu đi từ Crossref đến vector index như thế nào?
Từ Crossref API -> `crossref.py` fetch và parse ra raw records (JSON) -> `cleaning.py` đọc raw records, lọc rác, xóa thẻ HTML, nối string thành cleaned dataset -> `embeddings.py/index.py` load file clean để chạy mô hình all-MiniLM sinh vector embeddings và đưa vào ChromaDB collection.
2. Evaluation set và ground-truth document IDs dùng để đo retrieval/answer quality ra sao?
`ground_truth_doc_ids` được so sánh với các doc ids mà ChromaDB trả về ở top-k để tính toán metrics như `retrieval_hit_rate` (tỷ lệ search đúng tài liệu). Câu `ground_truth` được đưa cho hệ thống Judge (LLM) đối chiếu với câu trả lời của agent để chấm điểm `judge_accuracy` hoặc tính `mean_token_f1`.
3. Quality checks khác freshness monitoring ở điểm nào trong bài lab?
Quality checks tập trung vào tính toàn vẹn/đúng đắn của cấu trúc dữ liệu (vd: schema hợp lệ, title/summary không null). Freshness monitoring là kiểm tra tính "mới mẻ" dựa trên cột `age_days` hoặc `published` có vượt mức cho phép so với hiện tại hay không.
4. Vì sao phải dùng cùng test set cho baseline, corrupted và repaired?
Để đảm bảo điều kiện kiểm soát (control group). Dùng 1 bài test cố định mới có thể phản ánh chính xác sự suy giảm khi dữ liệu bị lỗi (corrupted) và sự phục hồi khi đã sửa (repaired) mà không bị nhiễu do test data thay đổi.
5. Repair được xem là thành công dựa trên artifact và metric nào?
Khi các metrics `retrieval_hit_rate`, `judge_accuracy`, và `mean_token_f1` ở pha Repaired có giá trị gần bằng hoặc bằng với pha Baseline ban đầu, và Data Quality report hiển thị "pass".
